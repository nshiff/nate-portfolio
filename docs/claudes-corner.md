# Claude's Corner

This file is maintained by Claude, for Claude. It is versioned with the rest of the codebase (unlike `MEMORY.md`, which is local and ephemeral), so notes here persist across machines and are visible in diffs/PR history to the user.

No permission is needed to edit this file — update it freely as you learn things worth carrying forward.

It has two parts, and they serve different purposes:

- **Current State** — what's true *right now*. No dates, no history. Rewritten in place as things change, not appended to. Read this first; it's the fast path to being useful in this repo.
- **Journal** — how we got here: decisions, overrides, things Nate explicitly chose against the obvious default. Dated, append-only, chronological. Read this when the *why* behind something in Current State matters, or before repeating a past mistake.

If something you're about to log is really just "the current architecture changed," update Current State and don't also spend a journal entry restating it. Journal entries are for the *reasoning*, the *override*, the *gotcha* — not a changelog of every edit.

## Current State

**Shape of the app.** Client-only React 19 + TypeScript SPA (Vite, react-router v8's data router), no backend. `src/App.tsx` defines one shared `Layout` (header/nav/footer) wrapping a `Home` route plus one explicit route per project (`/project/01`, `/project/02`, ...) — there's no dynamic `/project/:id` route. Adding a project touches three places: `src/data/projects.ts`, a new `src/pages/ProjectNN.tsx`, and a new route + import in `App.tsx`.

**Source of truth for the project list.** `src/data/projects.ts` is a flat array of `Project` objects (id, title, description, emoji, gradient background, category). `Home.tsx` reads it to render category sections and a featured strip. IDs are zero-padded two-digit strings, *not* contiguous/ordered in the array (grouped by category instead). Id `17` (Cloth Simulation) is permanently absent — removed deliberately due to a Vite dev-server warning that couldn't be fixed; don't reintroduce it casually.

**Two ways a demo gets embedded:**
1. **Sandboxed iframe** (the default — most demos work this way): the page component renders `<iframe src="/demo/whatever.html">` pointing at a fully self-contained static HTML file in `public/demo/`. Own script tags, no build step, no access to the app's React tree.
2. **Inline React component** (exception, not a pattern to extend): a few demos (`ModularSynth`, `DoubleSlitVisualization`, `NavigatorDashboard`) are `.jsx` files in `src/components/` with a hand-written sibling `.d.ts`, imported directly into the page tree — `.jsx` in an otherwise all-TypeScript codebase, because they were dropped in from AI-generated canvases with minimal porting.

**Styling.** Vanilla CSS is the standard: inline `style={{}}` objects using CSS custom properties (`var(--text-secondary)`, `var(--accent-color)`, `var(--border-color)`, etc.). Tailwind is a dependency but is an intentional one-off, used only by `ModularSynth.jsx` because that's how Gemini originally built it — don't reach for Tailwind classes on new work just because the dependency is present.

**Provenance is part of the product.** The README and several project pages explicitly credit AI tools (Gemini Canvas, Claude) as co-authors of individual demos, with source links back to `public/demo/*.html` on GitHub. This portfolio is partly about showcasing AI-assisted build velocity — weigh that when deciding how much to polish vs. preserve a piece's "as generated" character.

**Testing.** `@playwright/test` is a real devDependency (Chromium in `~/.cache/ms-playwright`). `playwright.config.ts` auto-starts `npm run dev` and points at `http://localhost:5173`; run the suite with `npm run test:e2e`. A Playwright script only resolves `@playwright/test` from inside the repo tree (needs `node_modules`) — a scratchpad/`/tmp` script fails with `ERR_MODULE_NOT_FOUND`. For a one-off visual check, write a throwaway `e2e/*.spec.ts`, run it, then delete it rather than leaving it in the permanent suite. `e2e/home.spec.ts` is the pattern for a real, permanent spec (navigate, assert visible text/roles) — keep new permanent specs low-effort/smoke-level unless asked for more.

**Project 20** is **Search Party**, living in `public/demo/zork-roguelike/` (directory name is stale — predates the current name, don't read anything into it). Dark terminal UI (`#0a0a0a` bg, monospace, bold 1.125rem output/input text). Terminal color (green/amber/white/default) is set via the `color` built-in command, not mouse UI — the old top-right swatch buttons were removed once the command shipped (2026-09-01); `--fg` CSS var still drives the color and still persists to `localStorage` under `searchparty-color`, just via `COLORS[name]` lookup instead of a click handler. `default` is a `COLORS` alias for green, not a separate hex. Built-in commands live in a single `COMMANDS` object in `game.js` (`{ run: () => "..." }`) — the dispatcher iterates it generically, so adding a command is a one-entry change. **Commands have no `help` field at all as of 2026-09-02** — that field was fully removed; `help`'s `run` now does `Object.keys(COMMANDS).sort().join("\t")`, i.e. the command's *object key* is its own help text. This is the second iteration of `help`'s format: first it went from descriptive strings to bare-name strings (confirmed deliberate), then the bare-name strings were dropped entirely in favor of reading the key. If a command ever needs a real description again, it can't just add a `help` field back to one command — the whole `help` command's `run` would need to change from `Object.keys` back to something that reads a per-command field, since the two are now structurally tied together. Current commands: `whoami` (→ `"player"`), `color <green|amber|white|default>`, `map`, `sleep` (room-gated — see `allowSleep` below; when allowed, random flavor text via a `pick()` helper, the same random-choice pattern the old WHO/WHAT/WHERE case data used, now reintroduced for a single command), `walk <room name>`, `help`, `exit`. The dispatcher (`handle()` in `game.js`) splits input into a command name plus a trailing arg string, passed as `command.run(arg)`.

**Rebuild toward a Carmen Sandiego / Clue-style tracker, foundation-first.** The previous incarnation (room graph you could `go`/`look` around, plus a randomized WHO/WHAT/WHERE "case" checked via `status`) was deliberately torn out (2026-09-01) to rebuild from a bare terminal shell up. Don't reach for that old room-graph code as a reference implementation without checking the journal — it was intentionally discarded, not just refactored. Nate's explicit approach (2026-09-02): nail down *gameplay feel* — the command vocabulary of a Zork-like — before any game logic, characters, or case content. He's building a candidate command list first (see journal) and implementing pieces incrementally: `map`, then `sleep`, then `walk`.

**Room graph model.** `ROOMS` is keyed by room id, and **the key IS the display name** — uppercase, **single-token, no separator** (`BEDROOM`, `LIVINGROOM`, `FRONTLAWN` — underscores were dropped from multi-word room names on 2026-09-02, after an initial pass used them; see journal for the history, but treat single-token-uppercase as current), shown to the player verbatim everywhere (map, walk destination text via `${id}`, etc.). There is deliberately no separate `name` field — Nate explicitly asked for it to be removed in favor of the key, and explicitly chose the literal-caps display over a humanized one when asked. **Don't add a `name` field back or humanize the display text without checking — this was a direct, confirmed choice, not an oversight.** Each entry also has `description` (short, shown on entry) and `adjacent` (array of neighbor room ids — **not** compass-direction exits like the old pre-reset model, since movement is `walk <room name>` not `go <direction>`). Currently 3 rooms: `BEDROOM` (start) ↔ `LIVINGROOM` ↔ `FRONTLAWN`, a simple chain — `FRONTLAWN` is only reachable via `LIVINGROOM`, not directly from `BEDROOM`. Adjacency is symmetric by convention (both sides of an edge list each other) — keep that when adding rooms. Rooms can also carry gameplay flags, checked by commands against `ROOMS[currentRoom]`: `allowSleep: true` is set on `BEDROOM`/`LIVINGROOM` but not `FRONTLAWN` (see `sleep` below) — this is the pattern to copy for any future room-dependent command (e.g. an eventual `search`/`accuse` might gate similarly). `currentRoom` (module `let`) and `visited` (`Set`, seeded with `START_ROOM`) track player state. Growing room-by-room as Nate requests them, not all at once.

**`map` command.** Lists visited-only room ids (which are the display names) in **alphabetical order** (bare `.sort()` between the `.filter()` and `.map()` — room ids are single-token uppercase ASCII, so default lexicographic sort is the intended alphabetical order, no comparator needed), current room suffixed `" (you are here)"`. Nate explicitly chose the plain-list rendering over an ASCII-grid layout when asked — simpler for now, may need revisiting once room count/spatial layout matters more. The alphabetical sort (added 2026-09-02) replaced definition-order, which would have looked arbitrary as room count grew.

**`walk <room name>` command.** Normalizes the arg to match key format via `toUpperCase()` only (no space-handling — room names are single-token now, so `walk livingroom` works but `walk living room` deliberately does not; Nate confirmed requiring single-token input over re-adding space-stripping when the room-name format changed on 2026-09-02) and checks it's in `ROOMS[currentRoom].adjacent`. On success: moves `currentRoom`, adds to `visited`, prints `describeRoom(destination)`. No-arg and invalid-target cases both return a plain error string, same convention as `color`.

**`describeRoom(id)` helper.** Renders a room as `${description}\nadjacent: ${adjacent.join(", ")}` — every full-room display (session intro, `walk`'s destination text) goes through this one function so they can't drift out of sync, same pattern as the pre-reset build's old `describeRoom`. Room `description` strings sometimes spell the room name in caps inline (e.g. BEDROOM's description reads "A small BEDROOM...") — that's deliberate flavor text matching the literal-key display convention, not a typo; keep that style if adding more rooms.

**Session intro.** On load, prints (in order): the `help` tip, then `describeRoom(START_ROOM)` — the old "Search Party." title-line print was removed on disk at some point outside an explicit request (like the `help`-string trims, presumably Nate editing directly in the IDE) and this doc previously described a title line that's no longer there; don't reintroduce it without checking. Keep the current ordering (tip before room description) if `START_ROOM` ever changes.
