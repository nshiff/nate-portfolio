# Claude's Corner

This file is maintained by Claude, for Claude. It is versioned with the rest of the codebase (unlike `MEMORY.md`, which is local and ephemeral), so notes here persist across machines and are visible in diffs/PR history to the user.

No permission is needed to edit this file — update it freely as you learn things worth carrying forward.

It has two parts, and they serve different purposes:

- **Current State** — what's true *right now*. No dates, no history. Rewritten in place as things change, not appended to. Read this first; it's the fast path to being useful in this repo.
- **Journal** — how we got here: decisions, overrides, things Nate explicitly chose against the obvious default. Dated, append-only, chronological. Read this when the *why* behind something in Current State matters, or before repeating a past mistake.

If something you're about to log is really just "the current architecture changed," update Current State and don't also spend a journal entry restating it. Journal entries are for the *reasoning*, the *override*, the *gotcha* — not a changelog of every edit.

## Current State

**Shape of the app.** Client-only React 19 + TypeScript SPA (Vite, react-router v8's data router), no backend. `src/App.tsx` defines one shared `Layout` (header/nav/footer) wrapping a `Home` route plus one explicit route per project (`/project/01`, `/project/02`, ...) — there's no dynamic `/project/:id` route. Adding a project touches three places: `src/data/projects.ts`, a new `src/pages/ProjectNN.tsx`, and a new route + import in `App.tsx`.

**Source of truth for the project list.** `src/data/projects.ts` is a flat array of `Project` objects (id, title, description, emoji, gradient background, category). `Home.tsx` reads it to render category sections and a featured strip. IDs are zero-padded two-digit strings, *not* contiguous/ordered in the array (grouped by category instead). Id `17` (Cloth Simulation) is permanently absent — removed deliberately due to a Vite dev-server warning that couldn't be fixed; don't reintroduce it casually.

**Two ways a demo gets embedded:**
1. **Sandboxed iframe** (the default — most demos work this way): the page component renders `<iframe src="/demo/whatever.html">` pointing at a fully self-contained static HTML file in `public/demo/`. Own script tags, no build step, no access to the app's React tree.
2. **Inline React component** (exception, not a pattern to extend): a few demos (`ModularSynth`, `DoubleSlitVisualization`, `NavigatorDashboard`) are `.jsx` files in `src/components/` with a hand-written sibling `.d.ts`, imported directly into the page tree — `.jsx` in an otherwise all-TypeScript codebase, because they were dropped in from AI-generated canvases with minimal porting.

**Styling.** Vanilla CSS is the standard: inline `style={{}}` objects using CSS custom properties (`var(--text-secondary)`, `var(--accent-color)`, `var(--border-color)`, etc.). Tailwind is a dependency but is an intentional one-off, used only by `ModularSynth.jsx` because that's how Gemini originally built it — don't reach for Tailwind classes on new work just because the dependency is present.

**Provenance is part of the product.** The README and several project pages explicitly credit AI tools (Gemini Canvas, Claude) as co-authors of individual demos, with source links back to `public/demo/*.html` on GitHub. This portfolio is partly about showcasing AI-assisted build velocity — weigh that when deciding how much to polish vs. preserve a piece's "as generated" character.

**Testing.** `@playwright/test` is a real devDependency (Chromium in `~/.cache/ms-playwright`). `playwright.config.ts` auto-starts `npm run dev` and points at `http://localhost:5173`; run the suite with `npm run test:e2e`. A Playwright script only resolves `@playwright/test` from inside the repo tree (needs `node_modules`) — a scratchpad/`/tmp` script fails with `ERR_MODULE_NOT_FOUND`. For a one-off visual check, write a throwaway `e2e/*.spec.ts`, run it, then delete it rather than leaving it in the permanent suite. `e2e/home.spec.ts` is the pattern for a real, permanent spec (navigate, assert visible text/roles) — keep new permanent specs low-effort/smoke-level unless asked for more.

**Project 20** is a from-scratch text-adventure REPL called **Search Party**, living in `public/demo/zork-roguelike/` (directory name is stale — predates the current name, don't read anything into it). Dark terminal UI (`#0a0a0a` bg, monospace, bold 1.125rem output/input text), three color-swatch buttons (green/amber/white, top-right) that set a `--fg` CSS var and persist to `localStorage` under `searchparty-color`. Built-in commands live in a single `COMMANDS` object in `game.js` (`{ help: "...", run: () => "..." }`) — `help` and the dispatcher both iterate it generically, so adding a command is a one-entry change. Current commands: `whoami` (→ `"player"`), `look` (describes the current room — see room graph below), `go <direction>` (moves through a room's exit), `status` (see below), `help` (lists commands + a plain-text tip about the color swatches, since they're mouse-driven UI and don't belong in `COMMANDS`), `exit` (ends the session, disables input). The dispatcher (`handle()` in `game.js`) now splits input into a command name plus a trailing arg string, passed as `command.run(arg)` — needed for `go north` etc.; commands that ignore the arg are unaffected.

**"The case" — Clue-style randomized premise, now a real room graph.** `WHO`/`WHAT` are still flat arrays of sci-fi-but-Calvin-and-Hobbes-silly flavor lines (imagination logic, not physics), one picked randomly per session into `theCase`. `WHERE` graduated from a flat array into `ROOMS`, a small object graph in `game.js`: 7 rooms (6 "candidate" locations from the original WHERE list, plus a neutral starting `hallway` that isn't itself a WHERE candidate), each with `name`, `look` text, and an `exits` map of compass direction → room id. `theCase.where` is a room id, picked from the 6 non-hallway rooms — it's the mystery's answer, shown by name via `status`, but is deliberately **not** where the player starts (Nate's call: closer to actual Clue, where the solution is separate from your position, and it gives exploration a point — see journal). Player position is `currentRoom` (module-scoped `let`, starts at `hallway`); `look` and `go`'s successful moves both render through one `describeRoom(id)` helper (room's `look` text + an `Exits: ...` line) so the two commands can't drift out of sync. Topology: `hallway` connects directly to all 4 of broomCloset/cafeteria/captainsOffice/deckGap; vendingNook and escapePod are one more hop out (via cafeteria and captainsOffice respectively). All rooms reachable from start. Content is still "good enough, iterate later" per the prior pass — same reasoning applies to room descriptions. No animations/visual flourishes — deliberately plain, per Nate's explicit direction. **Live and deployed** as of the "bold text" pass — Nate has committed and pushed this, so it's not just local iteration anymore.

## Journal

### 2026-08-17 — Tailwind and the missing id 17, confirmed

Early orientation raised two questions; Nate answered both (now folded into Current State above, kept here for the *why*): id `17` (Cloth Simulation) was removed on purpose after a Vite dev-server warning that a refactor attempt failed to fix — matches `git log` (`ed70512`). ### 2026-08-17 — Wave Function Collapse (Project 19): shipped as spec'd, banding is expected

Built from a GIVEN/WHEN/THEN spec (`docs/BehavioralSoftwareRequirements.md`, now implemented into `public/demo/wave-function-collapse.html` — that spec file can probably be archived). The spec's compatibility rule is strict, non-rotational edge-label matching, which — with a 9-tile terrain set and one fixed orientation per tile — means propagation can't turn corners: it settles into either one flood-filled terrain or straight bands, never organic 2D blobs. Verified live via Playwright, zero console errors, just visually stripe-y rather than blob-y. Asked Nate whether to add rotated tile variants (would allow corners/islands) or ship as spec'd — **he chose ship-as-spec'd**, the literal spec behavior is what matters here, not visual variety. Don't "fix" the banding later without checking that preference still holds.

### 2026-08-20 — Boids (Project 20, first attempt): built, then reverted mid-session

Built a full Boids flocking simulation matching the portfolio's visual conventions, verified working, before Nate changed direction to focus on Playwright tooling instead. He reverted `Project20.tsx`/`boids.html` himself, which briefly broke the dev server until the leftover `App.tsx`/`projects.ts`/`index.css` wiring was reverted too. This attempt is now purely historical — Project 20 has since been rebuilt from scratch as something unrelated (see Current State) — but the visual approach (dark panel `#0F1115`/`#15181E`, JetBrains Mono, `.wrap`/`.controls`/`.stage` structure) is worth reusing if a Boids-style demo ever comes up again, in this slot or another.

### 2026-08-24 — Project 20 churned through five identities in one session; landed on Search Party

In order: an explicit "coming soon" placeholder (genericized after initially reusing Boids' category/emoji) → wired to a pre-existing `zork-roguelike/` demo → described as "LOWTOWN" after reading its then-current code → superseded when Nate reset the demo file to a bare stub and renamed the project to **Search Party**, a "Zork-like." Each pivot's page copy, `projects.ts` entry, and iframe target were fully reconciled to match — no stale references were left behind at any step. This churn wasn't indecision to avoid next time: see the feedback memory `feedback_iterative_style_audit` — Nate builds incrementally partly *because* it's how he confirms Claude is actually following this repo's informal conventions before trusting it with more scope. Don't rush to lock scope early when this happens again; it's the intended way of working here, not friction.

### 2026-08-24 — Search Party gets a real room graph; theCase.where separated from player start

Built dynamic `look` the "for real" way (Nate's explicit choice over a lighter template-only option): `WHERE`'s 6 flavor strings became an actual `ROOMS` graph with compass exits and a `go <direction>` command, replacing `look`'s old fixed string. One open question Nate deliberately declined to answer ("no preference... sounds like an implementation detail") was whether `theCase.where` (the random WHERE pick shown by `status`) should double as the player's starting room, or stay independent and have the player start elsewhere and travel to it. Decided independent, on judgment rather than instruction: starting *in* the answer room makes the WHERE roll narratively inert — `status` would just describe where you already are, nothing to explore toward. Added a 7th room, `hallway`, as a neutral non-candidate starting point instead. If this ever feels wrong in play (e.g. too much wandering before anything relevant happens), that's the seam to revisit — it was a judgment call on a question Nate explicitly left open, not a settled requirement.
